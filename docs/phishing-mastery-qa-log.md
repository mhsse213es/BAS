**What's unverified:** the real `signInSessionsValidFromDateTime` propagation timing in production (this session's tests simulate a 2-poll delay; real Entra ID propagation delay is undocumented and could exceed the 3-attempt/2s default budget), real Graph throttling behavior under `RevokeAndVerifySignInSessions`'s retry loop, and whether `CreateSharingInvite`/`CreateCalendarEventLure`'s read-back verification races against real Graph eventual consistency the way the fixture tests assume it doesn't.

**Resolution path:** confirm the real field names against each vendor's own official API reference (requires a developer-portal login for CrowdStrike, or testing against a live console for either) — not something to fabricate from third-party docs alone.

### PH-DET-002 (user-reported phishing / SOC triage) — RESOLVED 2026-10-18

### Real phishing scenario run execution, persistence, and reporting pipeline — RESOLVED (vertical slice) 2026-10-18

Before this closure there was no phishing scenario run-execution, persistence, or per-run report pipeline anywhere in the product — only this file's own 44-entry catalog and the static industry-profile report (`internal/reporting/phishing_industry_profiles.go`) existed. `phishcatalog.Scenario.MappedImplementation` was (and remains) documentation text only, never a callable reference: nothing let an API call "run PH-DET-002" and get back a persisted, retrievable, client-readable result. Built the full pipeline for exactly one scenario — PH-DET-002 — as the smallest complete vertical slice, per the user's own explicit instruction to prove the mechanics end to end before expanding across the catalog, rather than building a parallel scenario engine or a report-only formatting shim over invented data.

**Architecture reused, not duplicated:** mirrors `internal/emailgwrun`/`internal/db/emailgwrun_store.go`/`internal/api/emailgwrun_executor.go`/`internal/api/emailgwrun_handlers.go` exactly in shape — same `Status` enum (pending/running/completed/failed/partial), same id/result/error/initiated_by/started_at/completed_at columns, same idempotent `CREATE TABLE IF NOT EXISTS` schema-ensure convention (no separate migration tool), same `auth.RequirePermission(auth.CanRunScenario)` gate on the trigger endpoint. New `internal/phishingrun` package holds the pure lifecycle types only (`PhishingRun`, `Status`) — deliberately not the executor/registry, after discovering mid-build that putting the registry there (which needs `phishbridge`→`emailgwefficacy`→`exercise`) created a real import cycle with `internal/db` (`exercise`'s own tests import `testutil`→`db`), the exact cycle `emailgwrun_executor.go`'s own package comment already documents as the reason EmailGW's executor logic lives in `internal/api`, not `internal/emailgwrun`. The scenario-executor registry (`internal/api/phishingrun_registry.go`, `LookupPhishingRunExecutor`) is the one place that makes a catalog scenario executable — only `"PH-DET-002"` is registered; every other of the other 43 catalog entries (including the 2 EXPERIMENTAL heuristics, PH-ID-004/005) returns 400 "not executable" rather than appearing runnable merely because it exists in the catalog.

**What's wired, specifically:** `POST /api/phishing-runs` (permission-gated, `InitiatedBy` always server-set from auth claims, never trusted from the body) → synchronous `ExecutePhishingRun` (PH-DET-002 has no real dwell window to wait out, unlike EmailGW's async goroutine) → `executePHDET002` builds a `phishbridge.ReportTicketExpectation` (always `ExpectedTicketCreated: true`, the catalog's own fixed `Expectation` — "known-good/known-bad" was a test-only concept, never a production run parameter) against an injected `ReportTicketEvidenceProvider` (nil until `Handler.WithPhishingRun` is called — a run then correctly completes with `Response.Verdict == NotTested`, never a fabricated pass/fail, since no real ITSM connector exists yet for this scenario) → persists the marshaled `phishval.Outcome` to the new `phishing_runs` table → `GET /api/phishing-runs/{id}` returns the persisted row → `GET /api/phishing-runs/{id}/report` renders client-facing HTML built exclusively from that persisted `Result` (`BuildPhishingScenarioReport`/`PhishingScenarioReportHTML`, mirroring `av_efficacy_scenario.go`'s visual layout) — deliberately never a live re-evaluation, since the acceptance criteria require the report to reflect exactly what was recorded, not a recomputation that could drift from it.

**EXPERIMENTAL visibility, closed for real this time:** the report's `Experimental` flag is detected from the evidence itself (`Evidence == EvidenceInferred` on any populated dimension), never from scenario-ID string matching — so it already generalizes correctly to PH-ID-004/005 the moment a future slice registers them, without any further report-layer change. When true, an unmistakable red/amber-bordered banner renders above the dimension list and above the catalog Limitations text, reading "EXPERIMENTAL — not a vendor-verified detection; see this scenario's own catalog Limitations below" — this is the concrete fix for the gap that triggered this whole build: an EXPERIMENTAL caveat that previously existed only in code comments and this QA log, with no path for a client reading an actual report to ever see it.

**Tenant isolation — flagged, not silently resolved:** `phishing_runs` carries no `tenant_id` column, matching the existing precedent of every sibling run table (`email_gw_runs`, `cloud_runs` — whose own `tenant_id` is the cloud *provider's* tenant concept, e.g. Azure AD, not Audspect's own multi-tenancy) rather than inventing isolation alone for phishing. `auth.Claims.TenantID` exists at the JWT layer but is not enforced as a row-scoping filter anywhere in this run-table family yet. **What it does:** PH-ID-001 (credential-harvesting simulation) grades `phishbridge.FromExerciseInteractionEvidence` against the catalog's own `InteractionClicked` expectation, reading the real evidence chain (`exercise.Store.ListEvidence`) for the `executionId` parameter.

**A real semantic correction made via TDD, not guessed:** the first draft of this executor's tests assumed "no evidence → NotTested," copying PH-DET-002's pattern. This is a different, and correct, semantic from PH-DET-002's "unconfigured provider" case, because here the evidence store genuinely is the complete record, not a possibly-absent external system. The test (`TestExecutePHID001_RealExecutionNoEvidence_Fail`) was rewritten to assert the real, documented behavior instead of "fixing" the executor to match a wrong assumption.

**A found-and-fixed real gap, also via TDD:** that same authoritative-absence design made an *unknown* execution ID dangerous — without an existence check, a typo'd or stale `executionId` would silently produce a confident `Fail` for an execution that never happened, exactly the kind of fabricated verdict this initiative forbids. Fixed by calling `exercise.Store.GetExecution` first and erroring (never grading) when it's not found — `TestExecutePHID001_UnknownExecutionID_ErrorNeverFabricatesFail` proves this.
