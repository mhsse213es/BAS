# TCF Roadmap — Phases 4-11 Sequencing

**Status: provisional sequencing, not eight approved specifications.** Each phase gets its own spec → plan → implementation cycle (same convention as `docs/superpowers/plans/`), starting with Phase 11. Phase 5 and Phase 6 may move earlier if Phase 4's composition design reveals that safety enforcement or validation evidence is a prerequisite for safely generating candidates.

**Rule: every phase starts with a fresh code-backed gap analysis before design.** The inventory below is a snapshot taken 2026-10-13, not permission to rebuild a subsystem that already works — re-verify it against current code before scoping each phase's spec.

## Sequencing principle

Dependency-aware, risk-first, delivering measurable value early — not cheapest-first. Implementation cost is a tie-breaker, not the primary driver. Analytics comes before automation because it gives the measurements needed to judge whether the automation that follows actually works.

## Sequence and rationale

1. **Phase 11 — Factory analytics.** Start here. Low cost · high leverage. Aggregate existing lifecycle, validation, provenance, and TCV records into trustworthy metrics — the baseline for pipeline health, content throughput, and threat-to-content latency before investing in larger automation.
2. **Phase 8 — Signing and air-gap distribution hardening.** Low-to-medium cost · high integrity value. **Spec written and approved (2026-10-13):** `docs/superpowers/specs/2026-10-13-tcf-phase8-airgap-signing-design.md`. Two rounds of code-backed gap analysis found this is a security-boundary defect, not a missing cosign integration: (1) the airgap install is currently broken end-to-end by a path mismatch (`pack.sh` stages images at `<bundle-root>/images/`, `setup.sh`'s glob looks one level off at `<bundle-root>/compose/images/*`) and fails only *after* `import.sh` has already loaded both Docker images and `setup.sh` has already written generated secrets to `${INSTALL_DIR}/.env` — this is the P0; (2) every verification stage silently degrades to "warn and proceed" instead of failing closed (missing `.asc`, missing `MANIFEST.sha256`, missing GPG key all proceed anyway); (3) the trust key (`pubkey.asc`) ships through the same channel as the bundle it verifies, which is not independent trust; (4) there is no rollback and no interruption detection — a killed mid-install silently regenerates and overwrites secrets on rerun. Cosign was investigated and resolved as providing no independent benefit: `pack.sh` generates `MANIFEST.sha256` before building and signing the tarball, so a mandatory GPG signature already transitively authenticates every file the manifest checksums (including both images) — `setup.sh`'s dead, unreachable cosign scaffolding is removed, not finished. Real per-artifact content signing (`internal/integrity`'s `CompiledVerifier`) is confirmed already correct and out of scope.
3. **Phase 9 — Threat-triggered generation observability.** Low-to-medium cost · closes a visibility gap, not a trigger-chain gap. **Correction (2026-10-13 re-verification):** the trigger chain already exists — `Scheduler.sync()` calls `Generator.Write` on every poll cycle unconditionally, and generation is already idempotent via `content_versions`' `(content_id, artifact_sha256)` dedup, with collision causes distinguished (`ErrSourceCollision`/`ErrOriginCollision`/`ErrThreatCollision`). What's actually missing: generation-attempt outcomes are only logged to stdout and an in-memory, process-lifetime counter (`Scheduler.status`), never persisted — so there is no durable failure visibility across restarts and no data to compute a duplicate-generation rate from. The real gap is a small persisted generation-attempt log, plus confirming whether re-running generation every poll (vs. only on genuine threat change) is a performance/noise concern worth addressing.
4. **Phase 7 — Approval pipeline extensions. DEFERRED (2026-10-14 re-verification) — no live remediation required.** Two rounds of code-backed gap analysis found the governance controls this phase's framing worried about are already solid for TCF's own output: the lifecycle state machine (`contentregistry/lifecycle.go`'s `transitionRules`/`CheckTransition`) is triple-enforced — application logic, `content_versions`' DB `CHECK` constraints, and an independent `content_version_events` audit-log `CHECK` that rejects a forged system-actor approval even via raw SQL — and a fourth layer below all of that: the app's own Postgres role (`db/app_role.go:90-94`) has `UPDATE`/`DELETE` revoked wholesale on `content_versions`, with exactly three columns (`lifecycle`, `trust_level`, `signature_bytes`) re-granted, and audit/safety-verdict tables have no write-back at all. Approval identity is derived only from authenticated JWT claims, never the request body, and is Admin-only. Publication is a real runtime gate (`gate.go`'s `ResolveExecutable`), not a label, and re-verifies signatures live rather than trusting a cached trust flag. RBAC has no drift for this subsystem. Every writer of `content_versions` was enumerated (exactly 3 production call sites, all invariant-preserving; everything else is compiler-excluded test code) — no bypass exists anywhere. TCF's own generated content is always `OriginLocal` (`generated.go:52`), and that path's `DRAFT → PUBLISHED_LOCAL` transition is clean and fully audited. The two gaps that *are* real — a `VALIDATING` lifecycle state with no legitimate way forward except rejection (zero production callers of the system-only transitions out of it), and a working `AttachVendorSignature` function (`gate.go:86-133`) with zero API route ever calling it — both turned out to be dead code: the one vendor-content source that exists today (`SourceBuiltin`, the shipped scenario catalog) has its own complete, non-bypassable trust check at intake time and never touches either path. Both are reserved integration points, most likely for Phase 6's unbuilt validator or a future vendor-intake source, not live risks. Decision: defer Phase 7 until a live consumer or concrete product requirement for either gap emerges; proceed to Phase 10 next per the existing sequence.
5. **Phase 10 — Customer-facing threat exposure.** Medium cost · visible customer value. Present threat relevance, affected techniques, evidence freshness, content availability, and validation status — clearly distinguishing observed evidence from inferred exposure and unknown coverage. Can be prototyped against existing evidence while the validation lab is still being designed, provided the UI labels evidence limitations honestly.
6. **Phase 4 — Content reuse and composition.** High cost · major capability expansion. Build the reusable composition layer that selects existing ART, Caldera, and Audspect behaviors before creating new candidates, enforcing provenance, compatibility, and safety constraints.
7. **Phase 5 — Safety engine extensions.** Dependent on composition requirements. Extend the current safety classifier to cover assembled content, not just individual scenarios. Preserve fail-closed execution and publication rules.
8. **Phase 6 — Automated validation lab.** High cost · infrastructure-heavy. The capability gap with the biggest implication for factory credibility. Build isolated execution infrastructure, telemetry collection, deterministic test cases, and evidence-backed validation.

## Adjustments baked into this sequencing

1. **Analytics metrics (Phase 11).** Threats ingested and resolved; candidates generated, rejected, validated, and published; median and P95 TCV; duplicate-generation rate; source-to-technique mapping coverage; validation results by content type. Only show a metric when its underlying data exists — use an explicit `NO_DATA` state when it doesn't, never a fabricated zero.
2. **Phase 8 is a release-integrity gate, not packaging polish — and is currently fail-open.** A correctly generated scenario is insufficient if the customer cannot reliably verify the integrity and authenticity of the imported bundle, and today they cannot: GPG is optional at every stage and `verify.sh` never checks a signature at all. Resolved: GPG becomes mandatory end-to-end (manifest is inside the signed scope, so it authenticates every file including both images — cosign adds nothing beyond that and its dead scaffolding is removed, not finished). Full design: `docs/superpowers/specs/2026-10-13-tcf-phase8-airgap-signing-design.md`.
3. **Phase 6 must not let `VALIDATED` imply more than it proves.** Until automated validation exists, the factory must distinguish content that parses and passes static safety checks, content that has executed successfully in a controlled environment, content whose expected detection was observed, and content whose detection outcome is unknown. A transition to `VALIDATED` must not imply all four unless the validation contract explicitly establishes that.
