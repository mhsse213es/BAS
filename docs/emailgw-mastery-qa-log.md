## Resolved items

### 1. M365 Defender enforcement-evidence/policy-configuration API path — RESOLVED 2026-10-15: a confirmed v1.0 Graph endpoint exists, no PowerShell needed

**Status:** Resolved by documentation research (not yet verified hands-on against a real tenant — that remains item #1b above). This reverses this item's original framing, which incorrectly assumed Exchange Online PowerShell with certificate-based auth was the only path; it is not.

**What was found:** Microsoft Graph's **`GET /security/collaboration/analyzedEmails`** is a **v1.0 (stable, not beta)** endpoint, namespace `microsoft.graph.security` — [List analyzedEmails](https://learn.microsoft.com/en-us/graph/api/security-collaborationroot-list-analyzedemails?view=graph-rest-1.0). It is the REST backing for the Microsoft 365 Defender portal's Threat Explorer, announced for programmatic use in July 2024 — [Announcing Microsoft Defender for Office 365 API's for retrieving threat data and remediating emails](https://techcommunity.microsoft.com/blog/microsoftdefenderforoffice365blog/announcing-microsoft-defender-for-office-365-api%e2%80%99s-for-retrieving-threat-data-an/4199777).

- **Permission:** Application (app-only) permission `SecurityAnalyzedMessage.Read.All`, least-privileged — **client-credentials OAuth2 against `graph.microsoft.com`, the exact same auth model and scope `internal/platform/msauth.EntraTokenSource` and `internal/vendors/defender.Client` already use.** No certificate-based auth, no PowerShell, no new credential/execution model needed anywhere in this codebase.
- **Query:** `startTime`/`endTime` plus OData `$filter`, confirmed filterable by `networkMessageId` and `recipientEmailAddress` (Microsoft's own documented example filters by both together).
- **Response carries both evidence legs Phase 3b needed:**
  - **Enforcement evidence:** `policyAction` (string), `policy` (string, which policy fired), `originalDelivery`/`latestDelivery` — each an `analyzedEmailDeliveryDetail` with `action` (`unknown|deliveredToJunk|delivered|blocked|replaced|unknownFutureValue`) and `location` (`unknown|inbox_folder|junkFolder|deletedFolder|quarantine|onprem_external|failed|dropped|others|unknownFutureValue`) — [analyzedEmailDeliveryDetail](https://learn.microsoft.com/en-us/graph/api/resources/security-analyzedemaildeliverydetail?view=graph-rest-1.0).
  - **SPF/DKIM/DMARC evidence (area A, exactly Phase 3a's own scenarios):** `authenticationDetails` — an `analyzedEmailAuthenticationDetail` with `dmarc`, `dkim`, `senderPolicyFramework`, `compositeAuthentication`, each a pass/fail/softfail string — [analyzedEmailAuthenticationDetail](https://learn.microsoft.com/en-us/graph/api/resources/security-analyzedemailauthenticationdetail?view=graph-rest-1.0).
  - **Detection correlation:** `alertIds`, `threatTypes`, `detectionMethods` — the same correlation `DefenderDetectionProvider` (Phase 3a) already does via `alerts_v2`, now available directly on the message record instead of needing a separate alert query.
  - **Correlation keys:** `networkMessageId`, `internetMessageId`, `recipientEmailAddress`, `subject`.

**What's still unverified (flagged honestly, not assumed):**
- **Finding the `networkMessageId` for a just-sent test message.** It's Microsoft-365-generated on acceptance, not known to `SpoofableSMTPInjector` in advance. Likely resolved by filtering `analyzedEmails` on `recipientEmailAddress` + the test's time window + matching `subject`/`internetMessageId` instead — ordinary correlation, not a structural blocker, but not yet proven against a real tenant.
- **Whether completely clean, non-malicious test mail (the "should deliver" legitimate-mail case) shows up in `analyzedEmails` at all**, or whether it's limited to mail with some analysis/threat signal. The Threat Explorer UI this API backs has an "All email" view suggesting yes, but this isn't stated explicitly in the property reference — verify hands-on.
- **Rate limits, pagination behavior (`$skiptoken`/`$top`), and whether `SecurityAnalyzedMessage.Read.All` alone suffices or a second permission is layered on in practice** — common gaps between a reference page and real tenant behavior.

**What this means for Phase 3b:** the implementation spec's "Scope Refinement" section is updated accordingly (§ below). The enforcement adapter is buildable now, httptest-backed, with zero new auth model — only real-tenant access (item #1b) gates the live integration test.

**Built, 2026-10-15 (`12d72380`):** `AnalyzedEmailEvidenceProvider` (`orchestrator/internal/emailgwefficacy/analyzedemail.go`), `defender.Client.QueryAnalyzedEmails` (`orchestrator/internal/vendors/defender/client.go`), and `DefenderMailEvidenceProvider` (composes it with `DefenderDetectionProvider` into one full `MailEvidenceProvider`). An httptest-backed end-to-end test (`TestDefenderMailEvidenceProvider_SPFScenario_EndToEnd_BothLegsSourceLive`) proves Phase 3's own exit criterion — both `Enforcement` and `Detection` evidence present and tagged `SourceLive` — for the SPF known-bad scenario. Only the real-tenant integration tests (`TestAnalyzedEmailEvidenceProvider_RealAPI_SkipsWithoutCredentials`, `TestDefenderDetectionProvider_RealAPI_SkipsWithoutCredentials`) remain skipped pending item #1b.

### 5. EG-001-EG-010 scenario catalogue gap analysis -- EG-002/EG-005/EG-009 built, 3 larger items explicitly deferred

**What was found (2026-10-16):** the client-facing EG-001-EG-010 scenario catalogue, checked directly against what Phase 3a/4 had actually built (not assumed covered). 6 of 10 were already covered (EG-001, EG-003, EG-004, EG-006, EG-007). **Built this pass** (`scenarios.go`/`scenarios_test.go`), at the user's explicit direction after reviewing the gap analysis:
- **EG-002 (executive impersonation)** -- `ExecutiveImpersonationExpectation`, deliberately kept distinct from the SPF/DKIM/DMARC scenarios (a freemail sender that itself passes SPF/DKIM/DMARC, with a forged display name -- a different control than sender-authentication alignment).
- **EG-005 (supplier payment diversion)** -- `SupplierPaymentDiversionExpectation`, kept distinct from EG-002 (external vendor, not internal persona) and from SPF/DKIM/DMARC (domain-reputation heuristics, not the message's own domain authentication).
- **EG-009 (authentication exception scope)** -- `AuthenticationExceptionScopeExpectation`. An explicit abstraction check was done before writing any code: does `MailExpectation` represent this outcome? Yes, once correctly split along the file's own existing `true`=benign/false=malicious-probe convention -- no new type family needed. Full reasoning in the architecture spec's Phase 7 amendment.
- **Regression, done explicitly per the user's own instruction**, not left implicit: all 6 pre-existing scenarios plus the 3 new ones pass; each new scenario has its own explicit "no evidence → `Inconclusive`" test, not just reliance on `VerifyMailExpectation`'s already-generic proof in `verify_test.go`.

**Update 2026-10-16 (same day): the Response/remediation dimension was built, closing EG-008 and EG-010 too.** Before building anything, a real evidence source was confirmed, not assumed: Microsoft Graph's stable v1.0 `security.alert` resource (the same `security/alerts_v2` endpoint `DefenderDetectionProvider` already queries for Detection) carries `investigationState` -- a fully-enumerated field (`successfullyRemediated`, `partiallyRemediated`, `benign`, `terminated`, `failed`, `running`, `pendingApproval`, etc.) -- plus `createdDateTime`/`resolvedDateTime`. No new vendor integration, no beta-API dependency (a separate beta `analyzedEmail: remediate` *action* API exists but is Microsoft-marked unsupported for production; only reading state was needed, not that).

- `MailEvidenceProvider` gained a third method, `ResponseEvidenceFor`. `FixtureMailEvidenceProvider` picks it up via a new `WithResponse` builder method, not a third constructor argument -- the existing two-argument constructor was already used across ~15+ call sites; a required third argument would have forced a `nil` everywhere for no benefit.
- `VerifyMailExpectation` gained `verifyResponse`, replacing the Phase 2-era hardcoded `ResponseVerdict: NotTested`. Same disjoint-evidence discipline as Prevention/Detection: a provider error or empty result both yield `Inconclusive`, never a fabricated `ConfirmedFailure`.
- `defender.Alert` gained `InvestigationState`/`ResolvedDateTime`, parsed from fields already present in the same Graph response `QueryAlerts` already fetches -- no new API call added.
- `DefenderDetectionProvider.ResponseEvidenceFor` maps `investigationState` to an outcome via two explicit sets (`successfulInvestigationStates`/`failedInvestigationStates`). Per the user's own explicit direction, `partiallyRemediated` and `benign` count as failure, not a weaker success -- "completed" means fully completed, and a controlled malicious test fixture is never genuinely benign. Any state outside both sets (still running/pending/queued/unknown) gets no record at all, so it falls through to the existing no-evidence→`Inconclusive` path rather than a fabricated verdict for work still in progress.
- **EG-008 (post-delivery threat response)** -- `PostDeliveryThreatResponseExpectation`. Unlike every other scenario builder in this file, it takes no boolean parameter: the premise (not caught at delivery, later re-evaluated as malicious) is fixed, and `MailExpectation` has no "expected response outcome" field -- Response is scored from whatever evidence a provider supplies, same as every other dimension. Proven fixture-backed (known-good/known-bad/no-evidence) and against the real adapter, including a dedicated test for the `partiallyRemediated`-is-failure rule and one for a still-`running` investigation producing no evidence at all (not a placeholder failure).
- **EG-010 (full detection→response chain)** -- closed by one end-to-end test where a single real Graph alert record serves as the source for *both* DetectionVerdict and ResponseVerdict, proving the chain is one correlated evidence source, not two independently-fabricated fixtures.
- Regression: every pre-existing test in both `internal/emailgwefficacy` and `internal/vendors/defender` passes unchanged. The now-false-premise test `TestVerifyMailExpectation_ResponseAlwaysNotTestedInThisPhase` was replaced with real coverage, not left in place contradicting the new behavior.
- §5 Coverage Matrix's area G row and the M365 Defender vendor row were stale ("no email-specific detection correlation exists yet" / adapter description missing the new Response leg) -- caught and fixed in the same pass, same discipline as Phase 6's own staleness catch.

**Update 2026-10-16 (same day): the four-state scenario-maturity model was built (`maturity.go`).** Locked at the user's explicit direction, with one strong correction to the initial proposal that shaped the whole design: maturity must be derived from actual recorded executions, never declared by hand. This same spec's own Coverage Matrix had already gone stale twice from a hand-maintained status (caught in Phase 6 and again in Phase 7) -- a maturity model with the same failure mode would be a worse version of the same problem, since "verified" is a stronger claim than a coverage row. A further explicit correction: a Go test passing is NOT, by itself, proof of verification -- the classifier consumes the real `VerdictDetail` and its backing evidence's `Provenance`, never a test's pass/fail signal.

- Four states, all computed: `MaturityNotImplemented` (no registry entry), `MaturityImplementedNotExecutable` (entry exists, nothing ever attempted), `MaturityExecutedWithoutEvidence` (attempted, but no qualifying record for every required ID -- fixture-only, `Inconclusive`/`NotTested`, or `Inferred` provenance all land here), `MaturityVerifiedThroughExecution` (every required ID has a record that is live-adapter-backed, definitive, and `Observed`).
- Per explicit instruction: a definitive `ConfirmedFailure` qualifies exactly like `ConfirmedSuccess` -- it proves a weakness exists, it does not mean the control passed, but it IS a valid verification of what actually happens.
- Both directions (known-good AND known-bad) are required per scenario, not just one -- applying scenarios.go's own stated principle ("a harness that can't prove both a pass and a fail is not yet trustworthy") to the maturity bar itself.
- EG-010 requires its Detection and Response records to share one `CorrelationKey` (the real alert's own ID) -- two independently-qualifying but unrelated records are explicitly NOT accepted as proof of the chain.
- Self-verifying, not self-declared: `maturity_live_test.go` runs every scenario's both directions through the real httptest-backed adapter and feeds the real resulting `EfficacyResult`s into the classifier -- including a capstone test asserting today's real, full 10-scenario state.
- **A genuine, previously-invisible gap surfaced by the model itself, not invented:** EG-007 (`SuspiciousAutoForwardExpectation`) has only ever had `FixtureInboxRuleProvider` -- no live/real adapter exists for inbox-rule evidence, unlike every `MailExpectation`-based scenario. It is correctly capped at `MaturityExecutedWithoutEvidence` until a real adapter is built for it.
- The tenant limitation stays explicit in the type's own doc comment: `ViaLiveAdapter`/"verified" means proof through the real adapter's HTTP/JSON code path (httptest-backed or real-tenant) -- never proof of effectiveness against an actual customer M365 tenant, which remains separately tracked as item #1b above.
- Scope boundary held exactly as instructed: `maturity.go` + registry + classifier + self-verifying tests only -- no dashboard, no Response/remediation changes, no new EG scenarios.

**Update 2026-10-16 (same day): scenario-maturity report built (`internal/reporting/emailgw_scenario_maturity.go`) -- but a bigger, real gap was found and surfaced first, not built past.** Checked whether EmailGW Mastery's scenarios are wired into the platform's actual run/execution pipeline the way other BAS verticals are -- they are not. ### 6. Real message injection wired into scenario execution (`injection.go`) -- a real mechanism found already built and never used, plus the real run-pipeline scoping

**What was found:** while scoping "wire EmailGW into the real run pipeline," two research passes ran in parallel.

**Finding A -- a real, complete injection mechanism already existed, unwired.** `internal/exercise/smtp_spoofing.go`'s `SpoofableSMTPInjector` was built specifically for EmailGW Mastery back in Phase 3's own design doc, with full control over envelope-from, header-from, HELO domain, and direct-to-MX or via-relay delivery. Its own `OriginLeg` type doc comment already named the exact connection point ("the sender-side half of `emailgwefficacy.OriginDeliveryObservation`"). But grepping the whole repo showed it was referenced only in its own file and its own test -- `internal/emailgwefficacy` never imported it, nothing called `SendTestMessage` from any scenario path. Built, tested, never integrated -- the same "evidence exists, nothing wires it into a real run" pattern as the rest of this initiative.

**Finding B -- the platform's real non-agent run pattern is smaller and more precedented than assumed.** `internal/cloudrun` is an existing, proven, *synchronous, non-agent* run model (a `cloud_runs` table, a plain Go function that inserts a `running` row, runs the real evaluation in-process, writes the final status+result, no queue, no polling, no agent) -- deliberately distinct from the agent-dispatch `ExecutionAttempt` model, which assumes an endpoint agent and doesn't fit EmailGW at all. This means wiring EmailGW into a real, persisted run pipeline is a genuinely tractable, well-precedented task (mirror `cloudrun`'s shape), not "comparable to Phases 1-7 combined" as first assumed before this research ran.

**Built this pass -- the injection half:**
- `MailExpectation` gains `EnvelopeFrom`/`HeaderFrom`. Empty `EnvelopeFrom` is a deliberate, checked "not wired for real injection" signal, not an oversight.
- `InjectScenarioMessage` (`injection.go`) sends the real message via `SpoofableSMTPInjector` and returns `OriginDeliveryObservation`'s sender-side half.
- **13 of 21 known-good/known-bad scenario directions are genuinely wired**; 8 are explicitly not, with the specific capability gap named in each one's own `Note`, not papered over:
  - SPF/DMARC's *aligned* case needs a lab domain whose SPF record genuinely authorizes Audspect's sending IP (DNS infrastructure, not code).
  - DKIM's *aligned* case needs real DKIM signing; the injector has no signing capability.
  - EICAR (either direction) needs a MIME attachment; the injector only builds a single-part HTML body.
  - Outbound DLP (either direction) is an authenticated-internal-sender scenario, not an externally-spoofable one -- a structurally different mechanism (e.g. Graph `sendMail`) would be needed.
  - The auth-exception-scope *genuine-use* case needs to send from infrastructure the exception's own verification condition actually trusts.
- Proven with an independently-built local `go-smtp` test server (the original helper in `smtp_spoofing_test.go` is unexported) -- a wired scenario's real send is observed on the wire correctly; an unwired scenario's empty-`EnvelopeFrom` check is proven to block the send entirely, never silently.
- `TestScenarioBuilders_NeverNameARealDomain` extended to also check `EnvelopeFrom`/`HeaderFrom` stay in the synthetic `.test` namespace.

**Still open, not attempted this pass:** persisting a run and polling for evidence after injection -- i.e. an actual end-to-end executable assessment, mirroring `internal/cloudrun`'s own pattern. This closes the "is there a real injection mechanism" question; it does not itself make EmailGW runnable as a persisted customer assessment.

### 7. Real EmailGW run persistence (`internal/emailgwrun`, `email_gw_runs`, `TriggerEmailGWRun`/`ListEmailGWRuns`/`GetEmailGWRun`) -- closes item 6's "still open" line

User explicitly scoped this before any code was written, in four points, and this pass followed that order exactly: (1) close the registry/`EnvelopeFrom`-validation gaps first, (2) build the table/store/API, (3) async executor + recovery, (4) single-scenario only, no campaign equivalent. The dwell-window number itself stays provisional by design -- configurable, with a conservative initial default, never hardcoded or invented per-scenario without reason, corrected later from real observed timing, never blocking the rest of the implementation.

**Gap 1 closed -- `emailgwefficacy.ExpectationByID` (`dispatch.go`):** resolves one of `EmailGWScenarioRegistry`'s own expectation IDs (e.g. `"EG-002.known-bad"`) back to a callable `MailExpectation`. This lookup only ever existed ad hoc, duplicated, inside `maturity_live_test.go`'s own test tables -- never production code. EG-007 is deliberately absent (not a `MailExpectation` at all -- a mailbox-rule check, not SMTP injection); EG-008/EG-010's four IDs all resolve to the identical `PostDeliveryThreatResponseExpectation()` call, since that scenario's "good"/"bad" outcome is decided by Defender's own post-delivery verdict, not by which message Audspect sends.

**Gap 2 closed -- `EnvelopeFrom` validated before any row exists:** `ExecuteEmailGWRun` resolves the scenario ID, then checks `EnvelopeFrom != ""` for all 21 known-good/known-bad directions, rejecting the 8 unwired ones (item 6's own list) with a clear error before ever inserting a row -- never letting one fail later, mid-wait, inside the background goroutine.

**Built -- the async executor, and the one deliberate divergence from `cloudrun`'s own shape:** `ExecuteCloudPlanRun` is a plain synchronous function because `cloudgraph.CloudPlan` has zero I/O. EmailGW's equivalent -- a real SMTP send, then waiting for a real mail gateway and a vendor API to produce evidence -- cannot finish inside one HTTP request. So `ExecuteEmailGWRun` inserts the row, injects the message synchronously (fast, fails fast on an injection error), and returns immediately at `StatusRunning`, while a detached goroutine (`finishEmailGWRunAfterWindow`, deliberately on `context.Background()`, never the triggering request's own context, which would already be canceled by the time the window closes) waits out the **dwell window** and calls `VerifyMailExpectation` exactly once -- it is already a one-shot full-window check, not a retry loop, so no polling machinery was needed at all.

**Dwell window, exactly as scoped:** `DefaultEmailGWDwellWindowPreventionDetection` = 5 minutes for ordinary scenarios; `DefaultEmailGWDwellWindowResponse` = 30 minutes for EG-008/EG-010, since Defender's own AIR/ZAP remediation completing is slower and less predictable than its delivery-time decision. `DwellWindowSeconds` on the request overrides either default, clamped to `[30s, 2h]`. Both defaults are explicitly provisional -- `EmailGWRun`'s own `InjectedAt`/`WindowStart`/`WindowEnd`/`VerifiedAt` columns exist specifically to collect the real timing evidence that would correct them later, per the user's own instruction not to invent numbers without evidence.

**A run completing its window is never read as the control passing or failing** -- this was an explicit instruction, enforced structurally, not just documented: `StatusCompleted` means every one of Prevention/DetectionVerdict/ResponseVerdict came back definitive; `StatusPartial` means at least one came back `Inconclusive`, i.e. real evidence was insufficient, never silently promoted either way. `StatusFailed` is reserved for the injection itself failing; `VerifyMailExpectation` never returns an error, so once injection succeeds a run always reaches `StatusCompleted` or `StatusPartial`, never `StatusFailed`.

**Goroutine durability, exactly as scoped:** `RecoverEmailGWRuns` runs at boot (backgrounded, never blocking startup) and resumes every row still at `StatusRunning` -- a row whose `WindowEnd` already passed is verified immediately; one still legitimately waiting gets a fresh goroutine for the remaining time. The original, persisted window boundaries are reused exactly, never extended. A row whose scenario ID no longer resolves is marked `StatusFailed` with a clear reason instead of left running forever. Timing evidence (injection time, window boundaries, completion time) is persisted on every row, per the user's own second requirement, for exactly the "correct the default from real behavior" purpose above.

**Import-cycle finding, worth keeping:** the executor could not live in `internal/db` the way `ExecuteCloudPlanRun` does. `internal/exercise`'s own tests import `internal/testutil`, which imports `internal/db`; `internal/emailgwefficacy` imports `internal/exercise` (for `SpoofableSMTPInjector`). Putting the executor's `emailgwefficacy` calls in `db` would close a cycle specific to `exercise`'s own test build. `internal/api` already imports both `db` and `emailgwefficacy` with no such problem, so `ExecuteEmailGWRun`/`finishEmailGWRunAfterWindow`/`RecoverEmailGWRuns` live there; only the plain CRUD store (`internal/db/emailgwrun_store.go`) stays in `db`, same as every other store.

**No credential UI, same posture as the Defender live adapter's own existing tests:** `AUDSPECT_EMAILGW_DEFENDER_TENANT_ID`/`_CLIENT_ID`/`_CLIENT_SECRET` (already the live-adapter test env var names) plus new `AUDSPECT_EMAILGW_INJECTION_HELO_DOMAIN`/`_TARGET_MX`/`_RELAY_HOST`, read once at server startup. `TriggerEmailGWRun` returns 503, never 500 or a silent no-op, when unset.

**Scoped deliberately narrow, exactly as directed:** single-scenario runs only -- no `cloud-campaigns`-style batch equivalent built.

**Proven real, not just compiled:** `internal/db/emailgwrun_store_test.go` (9 tests, real Postgres via testcontainers) covers schema idempotency, the status check constraint, insert/get round-trip, the injected/running transition, both terminal transitions, list ordering, and the running-only filter recovery depends on. `internal/api/emailgwrun_executor_test.go` (16 tests) and `emailgwrun_handlers_test.go` (8 tests) cover: unknown/unwired scenario IDs rejected before any row exists; a real send through a local SMTP test server; the prevention/detection vs. response dwell-window defaults and clamping; `StatusCompleted` vs. `StatusPartial` derivation from real `VerifyMailExpectation` output (both an all-definitive and an all-`Inconclusive` case); the recovery sweep actually re-verifying an already-past-window row end-to-end and marking an unresolvable scenario ID failed; and the full HTTP surface (503 unconfigured, 400 missing/unwired scenario ID, 201 success, `InitiatedBy` never trusted from the body, list/get round-trips, 404). `internal/testutil/testdb.go` gained `EnsureEmailGWRunSchema` alongside `EnsureCloudRunSchema` so every other package's test harness has the table too.

**Still open:** no aggregation or dashboard reads `email_gw_runs` yet -- this pass makes EmailGW runnable as a real, persisted assessment; turning that history into customer-facing metrics (detection speed, evidence completeness, regression over time) is a separate, not-yet-scoped follow-on, same as this initiative's very first table named it before any of this existed.

### 8. EmailGW runs summary (`GET /api/emailgw-runs/summary`) -- closes item 7's "still open" line, scoped before building

User was presented three real options before any code: (1) a JSON-only compute-on-read endpoint mirroring `cloudrun`'s own `cloudCampaignRollup`, no new table; (2) the same plus a static rendered HTML report, matching the `emailgw_coverage`/scenario-maturity report precedent; (3) a full `internal/dashboard`-style scheduled, persisted time-series snapshot. **User chose option 1, and explicitly deferred MTTD/MTTR** (this codebase's own existing mean-time-to-detect/respond naming -- already used throughout `internal/exercise`/`internal/reporting`, reused rather than inventing new terminology) to a later pass, once there is enough real run volume to average meaningfully.

**Why MTTD/MTTR were held back, not just skipped:** there are zero real customer runs in `email_gw_runs` as of this pass -- every row so far is this session's own test data. A mean computed over that would be decorative, not real; the same "vacuous score" problem `internal/dashboard`'s own `Snapshot.HasAttackPathData` flag exists to call out explicitly rather than silently present a 0/100 as if it meant something.

**Built:**
- `buildEmailGWRunsSummary` (`internal/api/emailgwrun_handlers.go`) -- a pure function over an already-fetched `[]*emailgwrun.EmailGWRun`: total + by-status counts, and a per-scenario breakdown (run count, by-status, and the latest run's own id/status/timestamp picked by real `StartedAt`, not list position -- `ListEmailGWRuns` already returns newest-first, but the aggregation doesn't rely on that ordering holding).
- `GET /api/emailgw-runs/summary` -- recomputed fresh on every request (no new table, no scheduler, no persisted snapshot), reading via `db.ListEmailGWRuns` with a higher default limit (1000, capped 5000) than `ListEmailGWRuns`'s own default (20): a summary is only as honest as the history it actually covers.
- Registered ahead of `/api/emailgw-runs/{id}` in `routes.go`. Proven through the REAL chi router (`api.Mount`, not a bare handler call that would bypass path matching) that `GET /api/emailgw-runs/summary` resolves to the summary handler and is never swallowed as an `{id}` value of `"summary"`.
- No new env vars, no new provider/credential wiring -- purely a read over data `ExecuteEmailGWRun`/`RecoverEmailGWRuns` already persist.

**Proven real:** 6 new tests in `internal/api/emailgwrun_summary_test.go` -- empty-input zero-value, by-status/by-scenario aggregation, latest-run selection by timestamp (not list order), first-seen scenario ordering, an end-to-end test against real inserted Postgres rows, and the route-resolution test through the real router.

**Still open, by design, not oversight:** MTTD/MTTR and any other time-based metric; a rendered dashboard page; a scheduled/persisted snapshot for real trend lines. All three wait on real run volume and/or a future explicit ask, not on anything technically missing.
