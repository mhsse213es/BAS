# Detection Rule Library (SP2) — Design

**Status:** Approved by user 2026-07-14, pending final spec review.
**Roadmap position:** SP2, next after SP1's first slice (see `[[project_platform_roadmap_2026h2]]` memory). Feeds directly into SP1's `internal/detectverify` connectors and the Detection Validation report.

## Why

Today an `ExpectedDetection` in a `scenarios/detection-profiles/*.yaml` file says "Microsoft Sentinel should detect this" — but there is no actual rule content behind that claim. An operator has to already own and maintain the detection. SP2 closes that gap: a curated, technique-indexed library of Sigma rules, each translated into every supported vendor's query language, browsable, exportable, and linked directly into the expectations that reference them. Combined with SP1, the platform can answer, per simulation: what should detect this, which vendors support it, which rule, and (via the existing Verification Store) was it actually verified.

**Explicitly out of scope for this slice** (deferred to future work, confirmed with the user):
- Pushing/deploying rules into vendor consoles via write APIs. This is a **read-only** content library — export only, operator deploys manually.
- Live "is this rule enabled in the vendor console" checks. A separate capability (list rules via the vendor API, match by identity) that needs its own design once the library's rule-identity model (below) exists to match against.

## Architecture

```
Python (dev-time only, never shipped, no runtime dependency introduced)
  scripts/rulelib-gen/
    load_sigma.py    — filter a curated local SigmaHQ checkout to rules tagging a
                        technique present in scenarios/detection-profiles/*.yaml
    translate.py      — pySigma + 5 backend plugins, per-rule per-backend, isolated
                        failure handling (one backend's failure never blocks others)
    validate.py        — quality gate (see Validation below)
    export.py          — writes internal/rulelib/ruledata/{rules.json,metadata.json}
    build.py            — thin entrypoint, runs the 4 stages in sequence

Go (runtime, embedded in the orchestrator binary — the same pattern as
    internal/reporting/attackdata's go:embed'd attack_enrichment.json)
  internal/rulelib/
    model.go     — Rule, LogSource, Translation types
    engine.go     — //go:embed ruledata/*.json; NewEngine(); schema-version check
    index.go       — in-memory technique/backend/status/severity/title indexes
    search.go       — Search(filter) combining any index dimension
    ruledata/
      rules.json    — committed to git; regenerated by hand when the curated rule set changes
      metadata.json — generation provenance + quality-gate audit trail
  internal/api/
    rulelib_handlers.go — read-only GET endpoints
  internal/scenario/
    ExpectedDetection gains one new optional field: RuleIDs []string
  wwwroot — new "Detection Rules" page + a link from Detection Validation report rows
```

The generator never runs as part of a build script (`packaging/windows-build.ps1` is unchanged) — it is a manual, occasionally-rerun tool whose output is committed, exactly like `internal/reporting/attackdata/gen/main.go`'s workflow today.

## Data Model

```go
// internal/rulelib/model.go
type Rule struct {
    ID             string   // stable, Audspect-owned identifier: "AUDRULE-000001"
    SigmaID        string   // upstream Sigma rule UUID — traceability only, never
                             // referenced directly by ExpectedDetection (Sigma IDs
                             // can be deprecated/renumbered upstream; ours can't)
    Title          string
    Description    string
    TechniqueIDs   []string // ATT&CK technique IDs; each validated at generation
                             // time against the bundled ATT&CK STIX data
    Severity       string
    Status         string   // Sigma "status": stable | test | experimental | deprecated
    Author         string
    References     []string
    FalsePositives []string
    LogSource      LogSource
    Detection      string   // the raw Sigma YAML block, verbatim, for the UI
    Translations   []Translation
}

type LogSource struct {
    Category string
    Product  string
    Service  string
}

type Translation struct {
    Backend     string    // provider-registry key: "microsoft_sentinel" | "microsoft_defender"
                           // | "splunk" | "elastic" | "crowdstrike"
    Language    string    // "KQL" | "SPL" | "Lucene" | "LogScale"
    Query       string
    Generator   string    // e.g. "pySigma 1.4.0 / pysigma-backend-splunk 2.1.0"
    GeneratedAt time.Time
}
```

**Backend list (verified 2026-07-14, corrected from the original draft):** 5 backends, not 6 — `pysigma-backend-qradar` requires an old, incompatible pySigma core (`pysigma<0.10.0`) that cannot coexist in the same environment as the other five (`pysigma-backend-kusto` for Sentinel, `pysigma-backend-microsoft365defender` for Defender XDR, `pysigma-backend-splunk`, `pysigma-backend-elasticsearch`, `pysigma-backend-crowdstrike` — all require `pysigma>=1.0`). QRadar is dropped from this slice; it isn't wired into `internal/detectverify` yet either. Revisit if QRadar's backend matures or when its connector gets built.

`internal/scenario.ExpectedDetection` (existing type) gains exactly one new field:

```go
RuleIDs []string `yaml:"rule_ids,omitempty" json:"ruleIds,omitempty"`
```

One technique commonly maps to several rules (e.g. T1059.001 → encoded-PowerShell, PowerShell-download-cradle, suspicious-child-process, AMSI-bypass rules), so this is a list, not a single ID. Omitted/empty is fully backward compatible — every existing `detection-profiles/*.yaml` file renders exactly as today.

## Generator Pipeline

Four stages, each its own Python module, run in sequence by `build.py`:

1. **`load_sigma.py`** — reads rules from a local checkout of the upstream [SigmaHQ/sigma](https://github.com/SigmaHQ/sigma) repository at a path the operator provides (e.g. `--sigma-dir`, same convention as the existing `attackdata/gen/main.go --sigma=DIR` flag). Obtaining/updating that checkout (`git clone`/`git pull`) is a documented manual prerequisite for running the generator, not something the script automates — the generator only reads, never fetches over the network, keeping it usable in an air-gapped dev environment too. It keeps only rules whose `tags` include an `attack.tXXXX` matching a technique ID already declared somewhere in `scenarios/detection-profiles/*.yaml`. This is the scoping decision: first slice covers only techniques the platform already ships detection-profile content for (~13 profiles today), not all of SigmaHQ.
2. **`translate.py`** — for each loaded rule, attempts conversion via pySigma against all 5 backend plugins independently; a conversion exception for one backend is caught and recorded, not propagated — the other backends still get attempted.
3. **`validate.py`** — the quality gate:
   - **Fails the build** (nonzero exit, nothing written) when: a rule has **zero** successful translations across all 5 backends; a rule's Sigma content is malformed; a rule tags a technique ID that doesn't exist in the bundled ATT&CK STIX; the output contains duplicate `AUDRULE-*` or duplicate upstream Sigma IDs; **any single backend's failure rate across all attempted rules exceeds 25%** (this is the systemic-regression guard — a backend plugin update or API-shape change that breaks conversion wholesale must block the build, not silently ship a gutted library for that vendor).
   - **Warns only** (recorded, build continues): an individual rule/backend translation failure below the 25% threshold — normal, expected variance in per-vendor Sigma coverage.
4. **`export.py`** — writes `internal/rulelib/ruledata/rules.json` (the `Rule` array) and `internal/rulelib/ruledata/metadata.json`:
   ```json
   {
     "schemaVersion": 1,
     "generatorVersion": "...",
     "sigmaCommit": "...",
     "generatedAt": "2026-07-14T00:00:00Z",
     "ruleCount": 47,
     "techniqueCount": 13,
     "backends": {"sentinel": 46, "splunk": 45, "elastic": 47, "defender": 44, "crowdstrike": 39},
     "translationFailures": [
       {"ruleId": "AUDRULE-000023", "sigmaId": "...", "backend": "elastic", "reason": "unsupported aggregation"}
     ]
   }
   ```
   `metadata.json` is a permanent, human-readable audit trail of exactly what the generator produced and what it skipped and why — not just counts.

Both JSON files are committed to git. Regeneration is manual (rerun `build.py` when the curated Sigma set or `detection-profiles/*.yaml` changes), never automatic.

## Runtime Loading & Degradation

`internal/rulelib.NewEngine()` parses the two embedded JSON files and checks `metadata.SchemaVersion` against the version this binary was built to understand. On a version mismatch, a missing/corrupt embed, or any parse failure: log a warning and return an **empty** engine — the rule library silently disables (search returns nothing, report rows render with no rule link) rather than blocking orchestrator startup. This matches the existing nil-safe-resolver pattern already used for `ScenarioResolver`/`VerificationResolver` in the reporting engine — a missing optional subsystem never takes down the core product.

## API (`internal/api/rulelib_handlers.go`)

Read-only, any authenticated role (`tierAny` — same tier as scenario/report reads in the RBAC matrix):

```
GET /api/rules                                          — paginated list
GET /api/rules/{id}                                      — one rule: full Sigma metadata + all translations
GET /api/rules/search?technique=&backend=&status=&severity=&logsource=&q=
GET /api/rules/technique/{id}                              — convenience wrapper over search
GET /api/rules/export?id=&format=sigma|kql|spl|lucene|logscale   — raw text download
```

Filtering is expressed as query parameters on one search endpoint, not a route per dimension (avoids route proliferation as filter dimensions grow).

## UI

**New "Detection Rules" page** (sidebar, under a new or existing Visibility/Operations section): browse and search by technique, vendor, status, severity, or free text; a rule detail view shows the full Sigma metadata (title, description, author, references, false positives, log source, raw Sigma YAML) plus every backend's translation side by side, each individually exportable/copyable.

**Cross-linking:** a Detection Validation report row whose expectation carries `RuleIDs` shows a "View Rules" link into this page, pre-filtered to those rules. The rule detail page, for any expectation currently referencing it, shows that expectation's live state pulled from the existing `verification.Store` (Detected/NotDetected/Pending, matched-alert summary, and investigation URL — all already captured by the SP1 connectors' evidence attachment and `Note` field). This closes the loop — **technique → rule → vendor translation → live verification → matched alert → investigation link** — entirely from data structures that already exist; SP2 adds no new verification plumbing, only the rule content and the linking field.

## Error Handling

- Generator: see Validation above — fail fast on structural problems (zero-translation rule, malformed Sigma, invalid technique ID, duplicate IDs, systemic backend failure); warn-and-skip on normal per-rule/per-backend gaps.
- Runtime: schema-version mismatch or embed/parse failure → empty engine, feature silently disabled, never blocks startup or any other page.
- API: unknown rule ID → 404; malformed search filter values → ignored (treated as "no filter on that dimension"), never a 400 — a browse/search page should degrade gracefully, not error out on a typo.

## Testing

- **Go (`internal/rulelib`):** unit tests against a small fixture `rules.json`/`metadata.json` — index correctness (technique/backend/status/severity lookups), `Search` filter combinations, schema-version-mismatch → empty-engine fallback, corrupt-JSON → empty-engine fallback.
- **Go (`internal/api`):** `rulelib_handlers_test.go` — httptest against the in-memory engine (no DB/container needed, since the library is pure embedded data), list/get/search/export, 404 on unknown ID.
- **Go (`internal/scenario`):** existing detection-profile YAML loader tests extended to confirm `RuleIDs` round-trips and that its absence doesn't change existing behavior.
- **Python (`scripts/rulelib-gen`):** fixture-based tests per stage — `load_sigma.py` correctly scopes to detection-profile techniques; `translate.py` isolates a per-backend exception; `validate.py` actually fails the build on a synthetic zero-translation rule and on a synthetic backend with >25% failure rate, and does NOT fail on an isolated single rule/backend gap below threshold; `export.py` produces well-formed JSON matching the schema above.

## Out of Scope (this slice)

- Live "is this rule enabled" vendor queries (future slice, needs its own design).
- Rule deployment/push automation (explicitly rejected — read-only library only).
- Full SigmaHQ bulk conversion (scoped to detection-profile techniques only; expand incrementally as new profiles are authored).
- Vendor-native rule packs (Splunk apps, Elastic detection packs, native Sentinel analytics rule templates) — noted as a natural future extension the current `Rule`/`Translation` model already accommodates without redesign, not built now.
