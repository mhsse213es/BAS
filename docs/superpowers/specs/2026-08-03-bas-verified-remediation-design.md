# BAS-Verified Remediation Validation — Design Spec

**Sub-project:** 5 of 6 in the Endpoint Health & Remediation initiative (1: Risk & Remediation view, 2: Security Config & Identity Posture Collection, 3: Patch Management & Application Risk, 4: Remediation Catalog & Single-Endpoint Execution, 5: this doc, 6: Enterprise ops tail — fleet comparison, exceptions, ownership/SLA, maintenance windows, batch remediation, MTTR)

## 1. Goal

Sub-project 4 answers "is the endpoint's configuration correct?" — its verification layer re-runs the finding's own `check_id` (a config probe) after a fix. That only proves a setting exists; it does not prove the setting actually stops anything. Sub-project 5 adds a second, independent verification layer that answers the stronger question:

> "Did the security control actually stop the attack?"

by re-running the real ATT&CK technique the control is supposed to defend against, through the existing BAS scenario-execution engine, and reading its real `PASS`/`FAIL`/`BLOCKED`/`ERROR`/`SKIPPED` verdict — the same verdict every other technique run in this platform already produces.

```
Remediation Request (Sub-project 4)
   ↓
Completed  (config verification passed)
   ↓  [separate, explicit trigger — not automatic]
Technique Verification (Sub-project 5)
   ↓
Real ATT&CK technique dispatched via Atomic Red Team
   ↓
models.CheckResult read directly off the result (no new taxonomy)
```

## 2. Architecture

### 2.1 Two independent verification layers — not merged, not shared lifecycle

Sub-project 4's config verification and Sub-project 5's technique verification stay architecturally separate:

- **Separate table.** `technique_verification_runs`, not an extension of `remediation_requests` or the unrelated `verification_history`/`verification_evidence` tables (those belong to the Detection Validation pack — a SOC analyst's manual attestation that a detection alert fired, a different concept entirely; reusing that name or those tables here would misleadingly conflate the two).
- **Separate trigger.** Config verification auto-continues from a fix dispatch (Sub-project 4's existing `handleRemediationFixResult` → `handleRemediationVerifyResult` chain). Technique verification does **not** auto-continue from that chain — it requires its own explicit `POST .../verify-technique` call. A real ART technique run is materially heavier and riskier than a config-check probe: it can trip EDR/SOC alerts and looks like genuine malicious activity on the endpoint, so it must never fire silently as a side effect of a routine config fix.
- **Separate finding lifecycle.** This is the one place a naive design breaks: `postureCheckInput` (Sub-project 2) only emits a `Finding` for a **currently-failing** config check — the instant that check passes, its `Finding` disappears from `GetAgentRisk` entirely. A control that's correctly configured (config check passes, no config `Finding`) but still lets the technique through must stay visible — the opposite of what the config-check lifecycle produces. So technique-verification findings are generated by an **independent** aggregation, reading `technique_verification_runs` directly, with their own `Finding.ID` (`checkID+":technique"`, never colliding with the config finding's plain `checkID`). See §6.

### 2.2 No new agent capability, no new dispatch pipeline

Technique verification reuses Sub-project 4's `dispatchRemediationStep`-style pattern (ephemeral, never-persisted `scenario.Scenario` + `scenario.BuildSteps` + `SendToAgent` + `SubmitScenarioResult`), with one difference: instead of a `Step{Framework: "custom", Command: <config command>}`, it dispatches `Step{Framework: "art", TechniqueID: <techniqueID>}` with **no** `Command` set. `buildStep`'s existing `case "art":` branch (`internal/scenario/builder.go:138-161`) already resolves the real atomic-test command from `h.artStore` for exactly this shape — the same mechanism every other ART-framework scenario in this codebase already uses. If the technique isn't in the local ART store, `buildStep` already degrades gracefully to a `SKIP:` command rather than erroring, which lands as `models.ResultSkipped` — no new error handling needed.

**V1 is ART-only.** Caldera-framework single-step dispatch exists in `buildStep` too (`case "caldera":`, calling out to a live Caldera server per step), but it has no offline fallback and adds a second dependency this sub-project doesn't need. Deferred, not built.

## 3. Eligibility

`EligibleForBASVerification(checkID string) bool` reuses Sub-project 4's own `findStepByCheckID` — no new mapping table, no invented technique links:

```go
func (h *Handler) EligibleForBASVerification(checkID string) bool {
	step, found := h.findStepByCheckID(checkID)
	return found && step.TechniqueID != ""
}
```

A check whose scenario step has no `technique_id` (e.g. `windows-bitlocker-enabled`, deliberately left unmapped back in Sub-project 2 because BitLocker has no honest ATT&CK fit) is simply **not eligible** — `POST .../verify-technique` rejects it, and no row is ever created. There is no `NOT_APPLICABLE` status value added to any taxonomy; "not applicable" is represented by the absence of a `technique_verification_runs` row, not a value within one.

## 4. Data Model

```sql
CREATE TABLE IF NOT EXISTS technique_verification_runs (
    id            text        PRIMARY KEY DEFAULT gen_random_uuid()::text,
    request_id    text        NOT NULL REFERENCES remediation_requests(id),
    agent_id      text        NOT NULL,
    check_id      text        NOT NULL,
    technique_id  text        NOT NULL,
    engine        text        NOT NULL DEFAULT 'art',  -- 'art' only in V1; column exists so Caldera is additive later
    run_id        text        NOT NULL DEFAULT '',      -- scenario_runs.id for the dispatch
    status        text        NOT NULL DEFAULT 'requested',
    reason        text        NOT NULL DEFAULT '',      -- human-readable detail from the result
    requested_by  text        NOT NULL DEFAULT '',
    requested_at  timestamptz NOT NULL DEFAULT NOW(),
    dispatched_at timestamptz,
    completed_at  timestamptz
);
CREATE INDEX IF NOT EXISTS idx_technique_verification_runs_request_id ON technique_verification_runs (request_id);
CREATE INDEX IF NOT EXISTS idx_technique_verification_runs_agent_id ON technique_verification_runs (agent_id);
CREATE INDEX IF NOT EXISTS idx_technique_verification_runs_run_id ON technique_verification_runs (run_id) WHERE run_id != '';
```

`status` values mirror `models.CheckResult` directly — `requested`, `dispatched`, then one of `pass` / `fail` / `blocked` / `error` / `skipped` on completion. No new enum; the same verdicts every scenario run already produces, read straight off the interpreted result.

Go type, `orchestrator/internal/remediation/technique.go`:

```go
package remediation

import "time"

type TechniqueVerificationRun struct {
	ID           string
	RequestID    string
	AgentID      string
	CheckID      string
	TechniqueID  string
	Engine       string
	RunID        string
	Status       string
	Reason       string
	RequestedBy  string
	RequestedAt  time.Time
	DispatchedAt *time.Time
	CompletedAt  *time.Time
}
```

## 5. API Surface

```
POST /api/remediation-requests/{requestId}/verify-technique
  → requires CanRunScenario (Analyst+Admin) — reused, not a new permission: this
    endpoint mechanically IS "run an ART technique against an agent", the exact
    action CanRunScenario already gates everywhere else in the codebase
  → 409 unless remediation_requests.status = Completed
  → 422 unless EligibleForBASVerification(check_id) (§3)
  → 409 if a technique_verification_runs row already exists for this request_id
  → dispatches Step{Framework:"art", TechniqueID: <from the check's own step>}
    via the ephemeral-Scenario pattern (§2.2), creates the row, returns
    {techniqueVerificationId, status: "dispatched"}

GET  /api/technique-verification-runs/{id}
  → poll status/reason (no lazy-timeout reaping in V1 — a single technique run,
    unlike a fix+verify+rollback chain, doesn't need it; can be added later if
    real usage shows hung ART runs)
```

### 5.1 The continuation hook

`SubmitScenarioResult` gains one more branch in its existing `continueRemediationFromResult`-style lookup (Sub-project 4, `internal/api/remediation_continuation.go`): if `raw.RunID` matches an open `technique_verification_runs.run_id`, interpret the result's `models.CheckResult` directly into `status`, copy the result's `Details` field verbatim into `reason` (the same field `models.SimulationResult.Details` already carries for every technique run — no new text to author), set `completed_at`, done. No fix→verify chaining here — a technique verification is a single dispatch, not a multi-phase state machine like Sub-project 4's fix/verify/rollback.

## 6. EndpointHealth Integration

A new aggregation, independent of `postureCheckInput` (§2.1), reads the latest `technique_verification_runs` row per `(agent_id, check_id)` and emits a `Finding` whenever that latest `status` is `fail` or `error`:

```go
// technique verification findings never come from postureCheckInput's
// pass/fail loop -- a config check that now passes must not silence a
// technique that still gets through.
func (h *Handler) techniqueVerificationFindings(ctx context.Context, agentID string, asOf time.Time) []endpointrisk.Finding
```

Each such `Finding` uses `ID: checkID + ":technique"` (distinct from the config `Finding`'s plain `ID: checkID`, so `diffFindings`' new/resolved trend logic and any ID-keyed lookup never collide the two). **These findings are appended to the `Security Configuration`/`Identity` category's `Findings` list only — they never change that category's `Score`.** Folding a technique-verification failure into the config score would re-merge the two layers this whole sub-project exists to keep apart; the config score stays purely config-based, and the technique-verification signal is a visible, separate finding plus a separate reporting metric (§7).

## 7. Reporting

A straightforward SQL rollup over `remediation_requests` + `technique_verification_runs` (no new subsystem): three independent percentages instead of one blended "remediation success" number —

- **Remediation Applied** — `remediation_requests` reaching `Completed` / total requested.
- **Configuration Verified** — same denominator, already exists (Sub-project 4's `Completed` status *is* config-verified).
- **BAS Validated** — `technique_verification_runs` with `status='pass'` / total `technique_verification_runs` rows (only among eligible, verification-attempted requests — never inflated by ineligible checks).

## 8. Explicitly Deferred

- **Caldera engine** — `engine` column exists for forward-compatibility; only `'art'` is ever written in V1.
- **Continuous/scheduled revalidation** (re-run BAS 24h/7d after a fix to confirm the control stays effective) — needs a job scheduler that doesn't exist anywhere in this codebase yet, same conclusion as Sub-project 4's Tier 3 deferral to Sub-project 6. Nothing in this sub-project's schema blocks adding it later — `technique_verification_runs` already supports multiple rows per `request_id` over time.
- **Lazy timeout detection** for `technique_verification_runs` (§5) — omitted for V1 pending real-world evidence it's needed.

## 9. Testing

- **Eligibility**: unit tests for `EligibleForBASVerification` against known eligible (`windows-firewall-enabled`, has `T1562.004`) and ineligible (`windows-bitlocker-enabled`, no technique) check_ids.
- **Dispatch**: DB-backed test asserting `Step{Framework:"art", TechniqueID:...}` is what gets built and sent — reusing Sub-project 4's `registerFixtureScenario`/`startFakeAgent` test pattern.
- **Continuation hook**: DB-backed tests for each terminal `models.CheckResult` value landing correctly in `technique_verification_runs.status`.
- **EndpointHealth integration**: test that a `fail` technique-verification row produces a `Finding` with `ID` suffixed `:technique`, that it doesn't change the category `Score`, and that it persists even when the underlying config check currently passes (the core §2.1 scenario).
- **RBAC**: extend `rbac_matrix_test.go` with the new route under the existing `CanRunScenario` permission — no new permission rows needed.
