# Remediation — Design Spec

**Date:** 2026-06-17
**Status:** Approved-with-changes (incorporates the `remediation.txt` review)

## Purpose

A prioritized, actionable **"how to fix"** view derived from open findings. It answers "what do I do about these gaps?" using **authoritative MITRE ATT&CK mitigations + detection guidance** — never fabricated steps. It is the natural companion to Findings: Findings is *what's exposed*; Remediation is *how to close it*.

Architectural placement (kept deliberately clean):

```
Runs         = persisted execution state
Campaigns    = computed aggregation
Findings     = persisted analyst state
Remediations = computed recommendations   ← this feature
```

**Remediations are computed-on-read. There is NO remediations table.** Findings own all state; the moment remediations grow `status/owner/due_date` we've built a second workflow engine — explicitly out of scope. When a finding resolves, its remediation simply disappears.

## Unit & grouping

One remediation = **one ATT&CK technique that has open findings.** Title = technique name; body = that technique's authoritative ATT&CK mitigations + detection guidance; it "closes" the open findings for that technique across agents.

## Backend — `GET /api/remediations`

Reads = viewer+. Groups open findings by `technique_id` and, per technique, returns:

```json
{
  "techniqueId": "T1003",
  "techniqueName": "OS Credential Dumping",
  "tactic": "credential-access",
  "severity": "Critical",            // worst severity across its open findings
  "controlClasses": ["Endpoint"],    // distinct control classes among its findings
  "findingCount": 18,                // open findings closed by this remediation
  "agentCount": 7,                   // distinct affected agents (kept separate from findingCount)
  "missed": 12,                      // exposure_state breakdown
  "detectedOnly": 6,
  "recommendedTargets": ["WIN-01","WIN-02"],  // affected agent ids — for future re-validate deep-link
  "mitigations": [                   // authoritative ATT&CK course-of-action
    { "id": "", "name": "Credential Access Protection", "description": "..." }
  ],
  "detection": "…ATT&CK detection guidance…"
}
```

- **Mitigation `id`** (M-code) is in the contract for forward-compat (reporting/cross-linking/audits). Our bundled `attackdata.Mitigation` currently stores `{name, description}` only, so `id` is empty until the enrichment bundle is regenerated from STIX to carry mitigation IDs — a noted follow-up, not v1. We do **not** fabricate IDs.
- **Sort order:** `severity DESC, missed DESC, agentCount DESC` — a Critical affecting 50 findings ranks above a Critical affecting 1.
- Source attribution: `mitigations`/`detection` are MITRE ATT&CK content; the UI labels them as such (see Honesty).

The grouping + worst-severity + sort is a **pure, unit-tested helper**; the handler queries open findings, runs the helper, and attaches `attackdata.Lookup(id)` mitigations/detection.

## Frontend — Remediation page

A new **Remediation** nav item (Visibility group, near Findings) + page:

- **3 stat tiles:** Open remediations (techniques) · **Affected findings** (open findings) · Critical remediations (techniques with a Critical open finding). *(Not "Gaps addressed" — that implies already-fixed.)*
- **Remediation cards** (sorted as above): severity badge, `technique-id · name`, control class(es), "Closes N findings on M agents", an exposure line **"Missed: X · Detected only: Y"**, and a **Re-validate** button.
- **Detail drawer** (reuses the results overlay): **ATT&CK Mitigations** list (name + description), **ATT&CK Detection Guidance**, affected findings (agent · status, each links to the finding), and Re-validate.
- **Re-validate** opens the run wizard so the analyst re-runs that technique against an affected agent. v1 opens the wizard; `recommendedTargets` is already in the response so a future version can pre-fill without an API change.
- **No greyed action buttons.** Export plan / Remediation report / Create Jira ticket are **not rendered** until the integrations exist (greyed buttons that do nothing frustrate users).

## Honesty

All remediation content is **authoritative MITRE ATT&CK** (mitigations = course-of-action; detection = ATT&CK detection guidance), explicitly labeled "ATT&CK Mitigations" / "ATT&CK Detection Guidance" so users know it is from MITRE — not generated by Audspect or an AI. We show **no "effort" rating and no "posture-gain points"** (we have no honest source); only real counts. This follows the platform's standing rule: ATT&CK enrichment is authoritative and attributed; nothing is fabricated.

## Testing

- Pure unit test for the grouping helper: open findings → per-technique remediation (worst severity, findingCount vs agentCount, missed/detectedOnly split, sort order).
- `internal/api` test for the handler response shape (grouped, sorted, mitigations attached).
- No tests against real/prod Postgres.

## Non-goals (v1)

A remediations table or any persistent remediation state (status/owner/notes/due-date), effort ratings, posture-gain projection, Jira/ticketing, export/report, and re-validate pre-fill. Findings own state; remediations stay derived. Mitigation M-codes await a bundle regen.
