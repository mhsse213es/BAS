# REQ-039 Level 5: key-management architecture

Status: DRAFT for review. Level 5 is not claimed. Criteria in `docs/security/req-039-customer-managed-keys.md` remain the acceptance bar.

## 1. Intent

Protect sensitive data with keys the customer controls, across its whole lifecycle, so that losing the Audspect host, its database, or its backups does not expose the data, and so that the customer can make the data unreadable by revoking a key.

Scope, as approved: connector credentials, the CA private key, configurations, run results, evidence, database backups and upgrade backups. The database TLS key is outside the envelope; it is handled by P0.1.

## 2. What exists today (the gap)

- Connector credentials are encrypted by PostgreSQL pgcrypto (`internal/secretstore/pgcrypto.go`). The symmetric key is a file on the host, `/etc/audspect/secrets/db-encryption.key`. Anyone with root on the host, or a copy of that file, can read every credential. This is the single point Level 5 must replace (req-039 P0.4).
- Backup archives are encrypted under a key that the installer generates on the host (`backup-key.sh`). The P0.3 recovery copy protects against losing that key, not against the host.
- The CA private key is wrapped under the database key (`ca-backup.sh`). The live CA key is a file on the host.
- Results, evidence and configurations are not encrypted by the application. They rely on disk encryption, which criterion 11 excludes.

## 3. Key hierarchy

```
KEK  (customer-controlled; lives only in the customer's provider: Vault, PKCS#11 HSM, cloud KMS)
 └─ wraps ─► DEK  (32 random bytes, generated by Audspect per value, held in memory only while in use)
              └─ AES-256-GCM ─► value (credential, result, evidence, configuration, backup, CA key)
```

- Each sealed value has its own DEK. A DEK is wrapped by the provider and stored next to its ciphertext. Compromise of one DEK exposes one value.
- The KEK is never returned by any interface. `internal/kms/kms.go` offers only `WrapDEK`, `UnwrapDEK` and `Status`. A provider that cannot meet this is not a provider.
- Every envelope is bound to its KEK reference and to a purpose label (for example `connector_credentials`). Authenticated data includes both, so a ciphertext copied into another table or purpose fails authentication.

Implementation: `internal/envelope` (Seal, Open). Blob format is versioned (`0x01`), so a future format can be read beside this one.

## 4. Provider interface

| Method | Contract |
|---|---|
| `WrapDEK(ref, dek)` | Encrypts the DEK under the KEK. Fails unless the key is active. |
| `UnwrapDEK(ref, wrapped)` | Recovers the DEK. Fails unless the key is active. |
| `Status(ref)` | Returns `active`, `disabled` or `revoked`. Any error means the caller fails closed. |

Providers are separate packages. Planned, in the order the customer needs them:

1. **Vault Transit** (`vault-transit`): customer runs Vault; Audspect calls `encrypt`/`decrypt` on a transit key that is marked non-exportable. Needs a Vault test instance to verify. Not built.
2. **PKCS#11** (`pkcs11`): customer HSM or SoftHSM. The KEK is an object with `CKA_EXTRACTABLE=false`. Needs a token to verify. Not built.
3. **Cloud KMS** (AWS KMS, Azure Key Vault, GCP KMS): same interface, one package each. Not built.

The in-memory provider (`internal/kms/memprovider`) is test-only and labelled so. It keeps keys in process memory and exists to test the envelope layer.

## 5. Revocation and cache rules

- **Status is checked on every Open.** The DEK cache saves only the provider's unwrap call. A cached DEK is never used if the KEK is no longer active.
- **Revocation invalidates cached key access immediately.** `Manager.Invalidate(ref)` zeroes every cached DEK for that KEK. A status failure invalidates too.
- **Fail closed.** If status cannot be confirmed, Open returns `ErrStatusUnknown`. There is no fallback to a previous answer.
- **Disabled is recoverable; revoked is not.** Disabling blocks use until the customer re-enables. A revoked key's data is unreadable by design, which is the customer's chosen outcome.
- **Bounded memory.** The cache has a maximum age (default 5 minutes) and a maximum size (default 1024). DEKs are zeroed on eviction and expiry. Go cannot guarantee erasure of copies the runtime has made, so this is a best-effort guarantee, and the spec says so.

Tests: `internal/envelope/envelope_test.go` covers revocation with a warm cache, disable and re-enable, status failure with a warm cache, cache hits and expiry, per-key invalidation, and wrong label, tampering and malformed input.

## 6. Where provider credentials are stored

The KEK never reaches the Audspect host. The host still needs credentials to call the provider (a Vault token, an HSM PIN, cloud IAM). Those are a separate secret, and they are a weaker thing to lose: they let an attacker use the KEK only while it is reachable and active, and the customer can rotate or revoke them without re-encrypting data. Their storage is an open decision (section 10).

## 7. Backups and restore are inside the boundary

- An archive is encrypted under a DEK. That DEK is wrapped by the KEK, and the wrapped DEK is stored in the archive header.
- Restoring on a new host therefore needs the provider to be reachable and the KEK to be active. This is intended. It is also a new dependency: if the customer's provider is lost, its backups are lost too.
- The P0.3 recovery copy is replaced by a provider-side recovery design. Until that is decided (section 10), backups stay under the P0.3 scheme and the envelope applies to new data only.
- Upgrade backups follow the same rule. A restore that cannot reach the provider must fail before any database change, which the restore pre-check already does for the CA key.

## 8. Migration: no installation becomes unrecoverable

The current pgcrypto values and the current backup archives must stay readable throughout.

1. **Dual read.** The store reads either format. A value in the old format is re-sealed on its next write.
2. **Re-seal job.** A deliberate, logged operation re-seals old values under the envelope, then verifies each one by opening it.
3. **Retire the key file last.** `db-encryption.key` is removed only after every value is verified and a restore from a new backup has passed on a clean host. Until then it stays.
4. **Populated-host validation.** The upgrade and restore path is tested on a host with existing data (criteria 9 and 10). Nothing in this section is tested yet.

## 10. Decisions (approved 2026-11-11)

1. **First production provider: Vault Transit.** Built against Vault's HTTP API (`internal/kms/vault`), with seven tests on a fake Vault server. It refuses exportable transit keys and treats a deleted key as revoked. **Verified against a real Vault** (Vault v2.2.1 (0e7c41b936218bd2401ab0f891c93bec10e2e8e4), built 2026-10-22T16:27:49Z, dev server, `hashicorp/vault:latest`): wrap and unwrap through Vault, refusal of an exportable key, and revocation after a real key deletion through the envelope layer. The integration tests skip unless `VAULT_TEST_ADDR` and `VAULT_TEST_TOKEN` are set. Dev mode is not a production Vault. PKCS#11 and cloud KMS follow.
2. **Level 5 requires a provider.** A host without a KMS or HSM is below Level 5 and is reported that way. No file-backed KEK is offered as a Level 5 option. **Policy recorded; enforcement not yet wired into the installer or the Level reporting.**
3. **Backup recovery when the provider is lost: escrow of the wrapped data key,** protected by its own passphrase, stored off the host like the current P0.3 recovery copy. **Design decided; not implemented.**
4. **Provider credentials on the host: a root-only token file, rotatable without touching data.** `vault.LoadToken` reads it. **Installer permission checks and rotation not yet implemented.**
5. **Audit: the existing `audit_logs` table,** which the runtime role cannot update or delete. **Decided; key-operation events not yet emitted.**

## 11. What is built with this document

- `internal/kms`: provider interface and status values.
- `internal/kms/memprovider`: test-only provider.
- `internal/envelope`: sealing and opening with revocation-checked caching. Twelve tests pass.
- `internal/kms/vault`: Vault Transit provider. Seven unit tests (fake server) and three integration tests pass against a real Vault dev server.

Connector credentials are wired. Setting `BAS_KMS=vault` (with `BAS_VAULT_ADDR`, `BAS_VAULT_KEY_NAME`, `BAS_VAULT_TOKEN_FILE`) makes new values sealed under the Vault KEK. Reads fall back to the legacy pgcrypto row only when no envelope value exists; a revoked key never falls back. `secretstore.Migrate` copies legacy values across and reads each back before counting it. Unset `BAS_KMS` keeps the existing store, unchanged. Tests: 23 secret-store tests against Postgres, plus an integration test against a real Vault that deletes the key and confirms the credential becomes unreadable.

Not yet done: the migration has not been run on any database, the legacy key file is not retired, and the CA key, configurations, results, evidence and backups still use their current schemes. Level 5 is not claimed.
