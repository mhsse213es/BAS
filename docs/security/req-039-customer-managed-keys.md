# REQ-039: Customer-managed keys at rest (Level 5)

Status: P0 code delivered on `main` (`bb787ada`), with the backup-key separation (P0.3) following on top. P0 is not closed: operational validation is outstanding (see "Not verified"). The full KMS work (P1/P2) is not started. Level 5 is not claimed.

Approved scope (2026-11-11): complete sensitive-data protection. This covers connector credentials, CA private key, configurations, results, evidence, database backups and upgrade backups. Host disk encryption is defence in depth only.

Architecture decisions (frozen):
- KMS behind an abstraction, not a vendor implementation. PKCS#11 and Vault first; AWS, Azure and GCP later.
- The root key-encryption key (KEK) is non-exportable and customer-controlled. The platform asks the KMS/HSM to wrap or unwrap data keys; it never receives the KEK.
- Envelope encryption. Data encryption keys (DEKs) are protected through their lifecycle, with explicit memory lifetime and cache limits.
- Revocation fails closed.
- CA signing uses an HSM where supported. Encrypting `ca-key.pem` under a DEK is not an acceptable end state.
- Keep Audspect deployable in isolated on-premises environments.

## P0.1 Database TLS: implemented

What changed:
- `db.Connect` calls `RequireVerifiedDBTLS` before any connection. It refuses every DSN that is not `sslmode=verify-full` with `sslrootcert`. `BAS_DB_TLS_DEV_INSECURE=1` is the only override, for development, and nothing in the installer sets it.
- Postgres runs with `ssl=on`, using a certificate generated by `packaging/compose/db-tls.sh` into `DATA_DIR/dbtls`. The certificate has SAN `DNS:postgres,DNS:localhost` and `CA:FALSE`.
- The orchestrator and auditcorpus connect with `sslmode=verify-full&sslrootcert=/etc/audspect/dbtls/server.crt`. They mount only the certificate, never the key.
- The installer creates the certificate on fresh install and on upgrade, before any service starts. An existing pair that does not verify (mismatch, garbage, expired, incomplete) is never overwritten. The installer stops with the reason.

Why this matters: on the staging host, `SHOW ssl` returned `off`, and none of the four live connections used TLS. Database traffic was plaintext.

Evidence:
- `TestRequireVerifiedDBTLS`: 9 cases (disable, prefer, require, verify-ca, missing root, missing sslmode, the dev override, empty DSN). Pass.
- `TestConnect_VerifiedTLSAgainstLivePostgres`: against a real `postgres:16-alpine` with the installer's certificate. The verified connection succeeds and `pg_stat_ssl` reports an encrypted session. A wrong CA is refused. A hostname outside the SAN (127.0.0.1) is refused. Pass.
- `packaging/compose/tests/db_tls_test.sh`: 11 pass, 1 skipped (Unix mode bits, which NTFS does not enforce; run on Linux).
- `docker compose config` renders the expected DSNs and mounts.

Limits:
- The certificate is a pinned self-signed leaf, so there is no second CA key. Rotation means regenerating it (move `DATA_DIR/dbtls` aside and rerun the installer), then restarting Postgres and the orchestrator. The orchestrator's single-file mount points at the old inode, so it must be restarted.

## P0.2 CA private key in backups: implemented

What changed:
- `packaging/compose/ca-backup.sh` stages the `pki` directory for a backup. It copies everything except `ca-key.pem` and writes `ca-key.pem.wrapped`, the key encrypted with the interim database encryption key (`/etc/audspect/secrets/db-encryption.key`, outside `DATA_DIR`). The wrap is verified by a round-trip before it is trusted.
- Both backup paths use it: the upgrade backup (`install.sh --upgrade`) and the backup engine's config archive (`_package_config`). The config archive's `pki` is staged, so no plaintext copy reaches the tar.
- If the wrap key is missing or unusable, the backup fails. There is no plaintext fallback. The upgrade stops before any change.
- Existing installations: the live `pki/ca-key.pem` stays where the orchestrator uses it. Earlier backups still hold plaintext keys. The upgrade lists them and asks the operator to remove them once a current backup is verified. This change does not delete any backup.
- Restore checks, before any database change, that the archive's wrapped key unwraps. After the config is extracted, it replaces the live key with the archived one. If that fails, the live key is put back and the restore stops.

Evidence:
- `packaging/compose/tests/ca_backup_test.sh`: 18 checks, all passing. They cover no plaintext in the staged copy, round-trip restore is byte-identical, a wrong key writes nothing, a missing wrap key fails closed, existing keys are never overwritten, the legacy-backup report, and the real `_package_config` extracted from `install.sh` (archive holds the wrapped key and the certificate, not the plaintext).

Limits:
- The wrap key and the wrapped backup are on the same host. Anyone with root on the host can unwrap backups. The backup is protected against copies taken off the host without the host's key directory. This is not HSM protection; that is P1.
- Restore onto a new host needs the database key too (`export-db-key` / `import-db-key`, see P0.4).
- Restore has not been run end to end on a host. See "Not verified".

## P0.3 Backup protection

Previous state (closed for new archives, see below): archives were encrypted with `DATA_DIR/.backup_key`, next to the archives. Anyone with an archive and that file could read the archive, which includes `.env` (database and JWT secrets).

Current state (`packaging/compose/backup-key.sh`):
- New archives are encrypted with `/etc/audspect/secrets/backup-encryption.key`, root-only (0600), outside `DATA_DIR`. It sits beside the database encryption key.
- New archives use only that key. If it is missing, the archive is not written. There is no fallback to the co-located key.
- Restore tries the new key first. The legacy co-located key is tried only for archives that do not open with the new key, and the restore prints a notice naming it.
- The legacy key is never deleted by the installer. It is removed only at the end of the historical cleanup below.
- Covered by `packaging/compose/tests/backup_key_test.sh` (13 checks): round-trip, a DATA_DIR-only copy cannot decrypt a new archive, no fallback when the new key is missing, legacy restore with notice, wrong key refused, legacy-key reporting.

Trade-off, accepted deliberately: a previous installer version cannot read archives made by this version, because it only knows the co-located key. Rolling back the software and then restoring an archive made after the upgrade therefore fails. To restore such an archive, use this version's installer, which keeps the new key. Do not copy the new key next to the archives to work around this.

Target: the archive key is wrapped under the customer KMS (P1). The new key is still a host-local key; a root user on the host can read it.

Recovery if the backup key is unavailable:
1. Restore the key from its offline copy to `/etc/audspect/secrets/backup-encryption.key` (owner root, mode 0600), then run `install.sh --restore <archive>`.
2. If no offline copy exists, archives made with that key cannot be decrypted. There is no fallback and no plaintext path. Make the offline copy as soon as the key is provisioned, and check that it opens an archive.

Historical cleanup (not yet done). Earlier backups hold plaintext CA keys (upgrade backups as `pki/ca-key.pem`; archives inside `.tar.enc`). Do not delete them immediately:
1. Create a new backup with this version. Verify its checksum.
2. Verify the CA key can be recovered from it (`ca_backup_unwrap` on its `pki` directory, or the restore pre-check).
3. Run a restore test on a clean host.
4. List every historical backup holding plaintext CA material: `ca_backup_plaintext_report` lists upgrade backups; archives must be opened with the legacy key to check.
5. Remove those backups with secure erasure. A filesystem delete does not erase data on SSDs or copy-on-write filesystems. Record what was removed and how.
6. Remove the legacy key `DATA_DIR/.backup_key` last, once no archive needs it.

Restore procedure (documented; not yet drilled):
1. Stop the service. Run `install.sh --restore <archive>`. Type `RESTORE` to confirm.
2. The installer checks the checksum, decrypts the archive, reads the manifest, and checks that the CA key unwraps. Any failure stops here with nothing changed.
3. A pre-restore snapshot is taken.
4. The database is restored, then the config, then the CA key is replaced from the archive.
5. Services start and the health check runs.

Required tests before this is Level 5:
- Fresh host restore from an archive, with the database key imported first.
- Restore with the wrong database key: must stop before any change.
- Rollback after a failed upgrade.

## P0.4 Key access and recovery: specification

Keys and who can read them on a Linux host:

| Key | Location | Mode / owner | Who can read |
|---|---|---|---|
| Database encryption key | `/etc/audspect/secrets/db-encryption.key` | 0640 root:65532 | root, the orchestrator group |
| Database TLS key | `DATA_DIR/dbtls/server.key` | 0600, owned by UID 70 | root, the postgres container |
| Database TLS certificate | `DATA_DIR/dbtls/server.crt` | 0644 | everyone (public) |
| CA private key (live) | `DATA_DIR/pki/ca-key.pem` | 0600, owned by UID 65532 | root, the orchestrator |
| Backup key | `/etc/audspect/secrets/backup-encryption.key` | 0600 root:root | root |
| Legacy backup key (historical) | `DATA_DIR/.backup_key` | 0600 root:root | root; removed after cleanup |

Authorization: only root on the host operates keys. Changing a key is an installer operation, not a database or API operation.

Audit: there is no key-operation audit yet. Key-operation audit at the KMS level is P1.

Rotation:
- Database TLS certificate: regenerate (see P0.1 limits).
- Database encryption key: no rotation procedure yet. Export and import exist (`export-db-key` / `import-db-key`). Rotation needs a re-encryption run and is P1.
- CA: rotation means a new CA and re-enrolling every agent. Not planned for P0.
- Backup key: no rotation procedure yet. Rotating it needs a new key and a re-encryption of retained archives, or keeping the old key for them (P1).

Recovery:

| Loss | Consequence | Recovery |
|---|---|---|
| Database encryption key | Stored credentials unreadable | Restore from the `export-db-key` recovery copy (passphrase protected) |
| CA key, with no backup | Fleet must re-enroll | Restore from a backup whose wrapped key unwraps |
| Database TLS material | Orchestrator cannot connect until regenerated | Move `dbtls` aside and rerun the installer, then restart |
| Backup key | New archives unreadable | Restore from the offline copy (see P0.3 recovery) |
| Host disk | Everything | Restore on a new host with the database key imported first |

Every recovery path needs the database key. It is the single point the Level 5 KMS work must replace.

## Draft acceptance criteria for REQ-039 (to freeze before P1)

Each criterion must have a test or an inspection that proves it.

1. No plaintext database connection: `SHOW ssl` on, and the orchestrator refuses any non-`verify-full` DSN. P0.1 test: met.
2. No plaintext CA private key in any backup or archive created by the installer. P0.2 test: met for new backups; legacy backups listed, not yet removed.
3. Every backup and archive is encrypted under a key that is not stored beside it. Met for new archives (P0.3, `backup-key.sh`). Not met for historical archives until the cleanup above is done; the legacy key is still beside them.
4. KEK never exported from the KMS/HSM. Not started.
5. DEK memory lifetime and cache limits are explicit and tested. Not started.
6. Revocation fails closed: a revoked key makes the platform unreadable, with a clear error. Not started.
7. Key operations are audited, attributable and immutable. Not started.
8. CA signing with the key inside an HSM where supported. Not started.
9. Restore drill passes on a fresh host, including the wrong-key case. Not run.
10. Upgrade and rollback pass on a real installation with existing data. Not run.
11. Results, evidence and configurations are encrypted at rest by the application, not only by disk encryption. Not started.

Level 5 is not claimed until 1 through 11 pass.

## Build and packaging

`packaging/build.sh` previously copied only some installer files. It did not copy `install.sh`, `db-encryption-key.sh` or `setup-install-state.sh`, which `install.sh` and `setup.sh` require. A bundle built from that script could not run the installer. It now copies all of them, plus `db-tls.sh` and `ca-backup.sh`. `packaging/compose/tests/bundle_helpers_test.sh` fails if any installer-required helper is missing from the build.

## Pre-existing test failures on main (not caused by this work)

Both fail on `9879b740`, the commit before the P0 work. Neither is run by CI (`.github/workflows/test.yml` does not invoke `packaging/compose/tests/`). Neither assertion has been changed.

- `packaging/compose/tests/db_encryption_key_test.sh`, "fresh install did not generate a valid key". Cause: `db_key_provision` verifies the key's owner and Unix mode itself, so it refuses on a filesystem without Unix modes (NTFS under Git Bash). On Linux the check is valid. Fix: run this suite on Linux in CI, or make the mode probe explicit in the test. Not yet done.
- `packaging/compose/tests/install_config_test.sh`, "upgrade did not keep it" (plus `command not found` for install helpers). Cause: the test runs `load_config` and other installer functions from a hand-written list of function names. That list has drifted from `install.sh`: `validate_k8s_scenario_config`, `validate_k8s_discovery_config`, `_stage_k8s_scenario`, `_stage_k8s_discovery`, `_write_aleef_secrets` and `info` are missing. Extracting every function by awk does not work, because a heredoc in `install.sh` has a line starting with `}`. The proper fix is a source guard in `install.sh` (so the test can source it) or a test that runs the installer's real entry point. Not yet done.
