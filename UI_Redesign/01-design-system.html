01 · Design system · v0.2

One set of tokens and components for every screen

Everything on this page is read live from assets/ds.css. Switch theme with T to see the dark and light steps; they are chosen separately, not inverted. v0.2 softened the whole palette — status and chart colours are desaturated, surfaces are calmer and the accent is gentler — while keeping every colour-blind and contrast check passing. Contrast ratios are computed in the page.

Rules that stop the drift

  • No raw colours. Every colour is a token (today there are 301 hard-coded hex values).
  • No inline styles. Components and utilities only, enforced by the existing g1d ratchet.
  • One component per job. One button, one tab, one table and one panel.
  • Status colours mean status. They are never used as a decorative series colour.

ColourSurfaces and ink

Navy surfaces sampled to match the logo. Text tokens are measured against --surface-1; all clear WCAG AA (4.5:1) on every surface in both themes.

ColourBrand and interaction

The accent comes from the shield logo's azure. It is used for interaction only (buttons, links, focus, selection), never to encode data.

ColourStatus and outcomes

A fixed four-step status scale with reserved meaning, always paired with an icon and a label (warning and serious sit below 3:1 on white by design). BAS outcomes map onto it, so “prevented” looks the same on every screen and in every report.

ColourData visualisation

The categorical slots come from a palette checked with a colour-vision validator: lightness band, chroma floor, separation under protanopia and deuteranopia, a normal-vision floor, and contrast against both surfaces. Single series use slot 1; outcome charts use the status scale; there is never a second y-axis.

TypeInter everywhere, JetBrains Mono for identifiers

Space Grotesk is retired; one sans for UI and numbers keeps hierarchy coming from size and weight, not from mixed faces. Large numbers use proportional figures; tables and axes use tabular figures.
